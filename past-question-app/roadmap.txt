For the **full MVP**, with payment handled on the website and the mobile app primarily serving as a secure reader for purchased past questions, I would structure the project into these major groups.

The key flow is:

**Web purchase → token generated → student registers/logs in with token → token verified by backend → purchased materials appear → student downloads encrypted content → reads offline in secure reader.**

---

### A. Onboarding

* Splash screen
* App logo/branding
* App introduction
* Basic onboarding slides
* Check app version
* Check internet connection
* Check authentication state

### B. Registration

Student enters:

* Token ID
* Email
* Password
* Name
* Phone number — optional

Backend verifies:

```text
Token exists?
        ↓
Token belongs to a valid purchase?
        ↓
Token already activated?
        ↓
Token still valid?
        ↓
YES → Create account
```

### C. Login

* Email/token ID + password
* Remember session
* Logout
* Session restoration
* Forgot password
* Password reset

### D. Student Home

Display:

* Purchased past questions
* Recently opened
* Continue reading
* Downloaded/offline materials
* Download status
* Profile

* Table of contents if available

* Bookmarks
* Reading position
* Recently viewed page

### Security

* No normal PDF download
* No "Open with..." option
* No sharing PDF
* No exporting PDF
* No printing
* No copy/export functionality where technically possible
* Screenshot protection
* Screen-recording protection
* Screen-mirroring protection where technically possible
* App-switcher privacy protection
* Dynamic watermark

Example:

```text
Licensed to:
Enoch Balogun

```

The watermark should be difficult to remove and ideally appear on the rendered content rather than being part of the original PDF.

# 4. Offline System

This is another major module.

### Initial download

```text
Internet
   ↓
Authenticate
   ↓
Verify license
   ↓
Download encrypted document
   ↓
Store securely
   ↓
Mark "Available Offline"
```

### Offline reading

```text
No Internet
    ↓
Open app
    ↓
Local authentication/session
    ↓
Validate local license
    ↓
Retrieve encrypted document
    ↓
Decrypt/render
    ↓
Read
```

### Offline features

* Open downloaded materials
* Continue from previous page
* Bookmarks
* Search
* Reading progress
* Notes if included in MVP
* Local license verification

### Important

The locally stored file should **not be a normal `.pdf` sitting in the user's accessible storage**.

It should be encrypted.

# 5. Token / License System

This is the bridge between the website purchase and mobile application.

### Token

Example:

```text
PQ-7F82-K91L-X82P
```

The token should be:

* Unique
* Random
* Hard to guess
* Associated with a product
* Associated with a purchase
* Activatable once or according to your rules
* Revocable

### Backend license

Something like:

```text
License
├── id
├── tokenHash
├── userId
├── productId
├── purchaseId
├── deviceId
├── status
├── activatedAt
├── expiresAt
└── createdAt
```

### License states

```text
UNUSED
ACTIVE
SUSPENDED
REVOKED
EXPIRED
```

# 6. Device Binding

You don't want:

```text
Student buys token
        ↓
Sends token to 20 friends
        ↓
20 people access the PDF
```

So:

```text
Token
 ↓
Account
 ↓
Authorized Device
```

Possible MVP rule:

**One token/account = one device.**

Or, more user-friendly:

**One account = maximum two devices.**

Features:

* Register device
* Device identification
* Device authorization
* Device removal
* Device replacement
* Maximum-device limit
* Revoke device
* Detect suspicious activation

# 20. Web Purchase Integration

Since you specifically said **payment happens on the web**, the mobile app doesn't need payment functionality in MVP.

Your architecture becomes:

```text
                 WEBSITE

Student
   ↓
Select Past Question
   ↓
Pay
   ↓
Payment Provider
   ↓
Payment Verified
   ↓
Generate Token
   ↓
Send Token
```

Then:

```text
                 MOBILE APP

Student
   ↓
Enter Token
   ↓
Backend
   ↓
Verify Token
   ↓
Create Account
   ↓
Attach License
   ↓
Show Purchased Materials
```

This is significantly simpler than implementing Apple/Google in-app purchases for V1.

# 21. Payment Backend Integration

Even though payment isn't inside the mobile app, your backend still needs to support the website.

For example:

```text
POST /payments/webhook
```

Payment provider sends:

```text
Payment successful
```

Backend:

```text
Verify payment
      ↓
Create purchase
      ↓
Create license/token
      ↓
Associate product
      ↓
Send token to customer
```

Your payment provider could be Paystack, Flutterwave, Stripe, etc., depending on the client's web setup.

# 32. What I would consider the actual MVP

Don't let the MVP become 50 features.

The **minimum production MVP** should be:

### Student

* Register with token
* Login
* View purchased materials
* Download purchased material
* Secure PDF reader
* Offline reading
* Reading progress
* Basic bookmarks
* Screenshot/screen-recording protection
* Watermark
* Device binding
* Logout

### Backend

* Authentication
* Token management
* License management
* Product management
* Document management
* Device management
* Secure document delivery
* Encrypted storage
* Offline license verification
* Audit logs

### Admin

* Admin login
* Add/edit products
* Upload PDFs
* Generate/manage tokens
* View students
* View purchases/licenses
* Revoke licenses
* View basic analytics

### Website

* Product catalogue
* Product purchase
* Payment verification
* Token generation
* Token delivery

That is the **real MVP**.

Everything else—advanced notes, highlights, AI explanations, practice tests, leaderboards, social features, sophisticated analytics, etc.—should come later.
